## 1. Executive summary

Продукт отвечает на один вопрос: **«что мне сегодня поставить в конфиг как рабочую модель, и изменилось ли что-то со вчера настолько, чтобы это трогать?»**

Не каталог. Не дашборд цен. Короткий список из 4–6 карточек с явной причиной и явным вердиктом.

Три вещи, которые определяют весь дизайн:

**Первое. Нулевой пользователь — автор.** Не комьюнити из 500 ИП. Критерий успеха PoC формулируется как фальсифицируемое утверждение: *«за две недели я хотя бы один раз изменил модель в своём Hermes `config.yaml` из-за этого артефакта — и не пожалел»*. Если не изменил — продукт не работает, и внешняя аудитория этого не исправит. Это прямое повторение траектории VkusVill-селектора: один реальный пользователь, ежедневное использование, потом уже всё остальное.

**Второе. Аудит данных дал результат лучше ожидаемого — но не там, где ожидалось.** OpenRouter отдаёт готовое поле `pricing.discount` и готовый Artificial Analysis intelligence index прямо в своём API. Оба — не на том эндпоинте, где их обычно ищут. Детали в разделе 5; практический вывод: **внешняя зависимость от Artificial Analysis для PoC и MVP-1 не нужна**, что убирает главный операционный риск. Одновременно latency/throughput в выборке оказались пустыми у 100% эндпоинтов — метрику «скорость» из ранних стадий вычёркиваем.

**Третье. Главный сигнал — исчезновение скидки, а не появление.** Появление скидки — приятная новость, на которую можно не реагировать. Исчезновение — это счёт, который вырос втрое, пока ты не смотрел. Асимметрия ценности здесь примерно 5:1 в пользу «пропало». Это диктует приоритет: change detection важнее ranking. Но это же — единственная функция, которую **невозможно** сделать в PoC, потому что для дельты нужна история, которой на день ноль нет.

**Четвёртое (добавлено в 1.1). Провайдер — второе измерение экономии, сопоставимое по величине с выбором модели.** Одна и та же модель у разных провайдеров стоит по-разному, и разброс достигает 5.5×. Эндпоинт `/models` отдаёт цену **дефолтного провайдера**, а не лучшего доступного. Продукт, построенный только на `/models`, систематически завышает цены и пропускает целый класс рекомендаций вида «ты платишь втрое больше за ту же модель». Модель перестаёт быть атомарной единицей рекомендации — единицей становится пара **(модель, провайдер)**.

**Пятое (добавлено в 1.2). Каталог из 415 моделей не нужен целиком.** Проверенный на данных **scope gate** (раздел 7.0) сокращает пространство до ~86 моделей, сохраняя 9 из 10 позиций топа по ценности. Экономия 78% запросов, снятие риска rate-limiting и — важнее — набор, который **можно проверить глазами**. 388 моделей проверить нельзя.

**Шестое (v1.2, проверено в 1.3). Data API работает и меняет карту источников.** `/api/v1/datasets/rankings-daily`, `/api/v1/benchmarks` и `/api/v1/classifications/task` протестированы живыми запросами: отдают объём токенов по моделям с историей от 2025-01-01, бенчмарки трёх источников и структуру спроса по типам задач. **`avg_cost_per_task` подтверждён как прямое измерение** (99 из 100 моделей на GPQA). Данные под **CC BY 4.0 с разрешением на republish** — лицензионный вопрос, ради которого Artificial Analysis выносился в validation-only, снят. Цена: инференс-ключ, 500 запросов/сутки на аккаунт.

Отсюда форма PoC: за первую неделю строится не столько продукт, сколько **накопитель истории**, а поверх него — минимальный shortlist, который уже полезен. Настоящая ценность включается на 8–10 день, когда появляются первые дельты.

**Рекомендуемая первая сборка:** статический сайт на GitHub Pages + `shortlist.json` + `report.md`, обновление раз в сутки через GitHub Actions с коммитом снапшота в репозиторий. Без бэкенда, без БД, без Telegram, без графиков.

## 2. Product goal

### Цель продукта

Сократить пространство из ~415 моделей до 4–6 названий с обоснованием, релевантным конкретной задаче пользователя, и предупреждать, когда экономические условия текущего выбора ухудшились.

### Цель проекта (отдельно, и она важнее)

Проект решает вторую задачу — **карьерную**. Он должен продемонстрировать роль PM / solutions architect через артефакт, а не через резюме:

- сформулирована фальсифицируемая гипотеза;
- проведён честный аудит данных с разделением «есть / платно / выводимо / нет»;
- scope нарезан по стадиям с явными критериями перехода;
- логика рекомендаций объяснима и задокументирована;
- есть работающий деплой и живой пользователь;
- отрицательный результат зафиксирован как результат, а не спрятан.

Эти две цели не конфликтуют. Более того: **отрицательный результат продуктовой гипотезы при качественно проведённом процессе — сильный карьерный артефакт.** «Я построил, измерил на себе, признал, что ценность ниже ожидаемой, и объяснил почему» читается зрелее, чем «я сделал дашборд, посмотрите какой красивый». Это надо заложить в дизайн сразу, а не оправдываться постфактум.

### Место в портфеле

```
bothub-llm-dashboard   →  сколько я УЖЕ потратил        (назад, факт)
LLM Discount Advisor   →  что выбрать ДАЛЬШЕ            (вперёд, решение)
Hermes Auto-Config     →  применить это одной командой  (действие)
```

Наблюдение → рекомендация → исполнение. По решению автора `bothub-llm-dashboard` развивается отдельной веткой (агрегация платных LLM API) и перекрёстных ссылок не требует. В спеке он больше не упоминается.

## 3. User segments and jobs-to-be-done

### Сегмент 0 — автор (единственный сегмент PoC)

| | |
|---|---|
| Кто | Разработчик-практик, гоняет Hermes Agent через OpenRouter, платит свои деньги |
| Контекст решения | Правка `config.yaml`: какая модель стоит основной, какая — для дешёвых массовых задач |
| Частота | Раз в 1–2 недели, плюс реактивно при скачке расходов |
| JTBD | «Когда я замечаю, что трачу больше обычного, я хочу за две минуты понять, что изменилось и на что переключиться, чтобы не проводить ревизию 400 моделей руками» |
| Что делает сейчас | Ничего систематического. Изредка заходит на страницу моделей OpenRouter, глазами не справляется, оставляет как есть |
| Почему это валидный сегмент | Реальные деньги, реальная ручка управления, ежедневное использование, доступен для интервью 24/7 |

### Сегмент 1 — AI-грамотный соло-разработчик / микрокоманда (цель MVP-1)

Похож на сегмент 0. Ключевой признак — **наличие ручки**: работает через API, может сменить модель конфигом. JTBD тот же. Проверяется после того, как продукт доказал ценность на сегменте 0.

### Сегмент 2 — комьюнити ИП, ~500 человек (источник фальсификации, не рынок)

Здесь нужна прямота. Человек, который делает карточки для маркетплейсов в Perplexity, **не выбирает модель**. У него нет ручки, которую крутит этот продукт. Для него «GLM 5.3 подешевел на 40%» — ноль информации: он платит фиксированную подписку и не видит токенов.

Его настоящий JTBD другой: *«я плачу за три AI-подписки, можно ли платить за одну»*. Это **другой продукт** — про схлопывание подписок, а не про выбор модели. Другие источники данных, другая логика.

Поэтому роль сегмента 2 в этой спеке: **не аудитория, а инструмент фальсификации**. Мы показываем им PoC не чтобы продать, а чтобы получить чёткое «нам не надо» и записать это как валидный learning. Если из 500 человек 5 скажут «о, полезно» — это сигнал, что подсегмент с ручкой существует. Если ноль — гипотеза о внешнем рынке закрыта за неделю, что стоит дёшево.

Ожидание по умолчанию: **отклик будет низким**. Планируем под это.

## 4. Product hypotheses

Каждая гипотеза сформулирована так, чтобы её можно было опровергнуть.

| # | Гипотеза | Как проверяем | Что считаем провалом |
|---|---|---|---|
| **H1** | Короткий shortlist полезнее полного каталога | Автор за 2 недели меняет модель в конфиге ≥1 раз по рекомендации | 0 изменений за 2 недели |
| **H2** | Ежедневных изменений цен достаточно, чтобы дайджест не был пустым | Считаем долю дней с ≥1 значимым изменением | <20% дней содержат событие |
| **H3** | «Скидка пропала» ценнее, чем «скидка появилась» | Автор фиксирует реакцию на оба типа событий | Реакция симметрична или на «пропала» реакции нет |
| **H4** | Данных OpenRouter достаточно без второго источника | Доля моделей shortlist с полным набором сигналов | <60% кандидатов имеют intelligence index |
| **H5** | График в PoC не нужен | Автор не испытывает потребности «увидеть поле» | Регулярно хочется scatter-плот |
| **H6** | Внешняя аудитория без API-ручки не является рынком | Отклик сегмента 2 | Неожиданно высокий интерес → пересмотр рамки |

H6 сформулирована как ожидание провала внешнего рынка. Это осознанно: если она **опровергнется** — это хорошая новость и повод расширять scope.

## 5. Data source audit

Аудит проведён эмпирически 19.08.2026: живые запросы к API, подсчёт заполненности полей на всех 415 моделях и выборке 274 эндпоинтов по 70 случайным моделям.

### 5.1 OpenRouter — первичный операционный источник

#### 5.1.1 `GET /api/v1/models`

Без авторизации, HTTP 200, **415 моделей**.

Заполненность полей верхнего уровня:

| Поле | Заполнено | Комментарий |
|---|---|---|
| `id`, `canonical_slug`, `name`, `created` | 415 / 415 | идентификация стабильна |
| `context_length` | 415 / 415 | |
| `pricing` | 415 / 415 | см. ниже |
| `architecture` (modality, input/output modalities) | 415 / 415 | фильтрация text/vision |
| `supported_parameters` | 415 / 415 | наличие `tools` — критично для агентов |
| `top_provider` (context, max_completion_tokens) | 415 / 415 | |
| `description` | 415 / 415 | текст, для карточки |
| `knowledge_cutoff`, `expiration_date` | 415 / 415 | часто null внутри |
| `reasoning` | 286 / 415 | mandatory / default_effort |
| **`benchmarks`** | **230 / 415** | **см. 5.1.2 — ключевая находка** |
| `alias_target` | 12 / 415 | алиасы вида `~z-ai/glm-latest`, надо исключать из ранжирования |

Поля `pricing` (значения — строки, USD за токен):

| Подполе | Заполнено |
|---|---|
| `prompt` | 415 |
| `completion` | 415 |
| `input_cache_read` | 247 |
| `web_search` | 157 |
| `input_cache_write` | 72 |
| `overrides` | 60 |
| `internal_reasoning` | 30 |
| `image` / `audio` / прочее | 9–32 |

Бесплатных моделей (`prompt == 0`): **20**.

**Ловушка `pricing.overrides`** (60 моделей): цена меняется в зависимости от длины промпта. Пример — `bytedance-seed/seed-2.0-code`: базовая ставка `0.0000005/0.000003`, но при `min_prompt_tokens >= 128000` она удваивается до `0.000001/0.000006`. Игнорирование overrides даёт **систематическую недооценку стоимости именно на длинноконтекстных задачах** — то есть ровно там, где деньги и утекают. В PoC обрабатываем как минимум флагом «цена растёт на длинном контексте».

**Слово `discount` на этом эндпоинте не встречается ни разу.** Как и `promo`, `sale`, `deprecated`. Это и есть источник распространённого заблуждения, что у OpenRouter нет скидок в API.

#### 5.1.2 Находка №1: Artificial Analysis уже внутри OpenRouter

Поле `benchmarks` присутствует у 230 моделей и содержит два провайдера:

| Провайдер бенчмарков | Моделей |
|---|---|
| `design_arena` | 230 (у всех, кто имеет `benchmarks`; массивы часто пустые) |
| **`artificial_analysis`** | **168** |

Структура `benchmarks.artificial_analysis` — ровно три подполя, все три присутствуют у всех 168:

- `intelligence_index`
- `coding_index`
- `agentic_index`

Ненулевой `intelligence_index` — у **149 моделей** (36% каталога, но покрывает практически все модели, которые реально рассматриваются как рабочие).

Пример: `z-ai/glm-5.3` → `{intelligence_index: 59.5, coding_index: 74.8, agentic_index: 59.1}`.

**Последствие для архитектуры.** Пара «цена + интеллект» — то, ради чего обычно строят интеграцию с Artificial Analysis, — доступна из **одного бесплатного неавторизованного запроса**. Второй источник данных из критического пути PoC и MVP-1 **исключается**. Это устраняет главный операционный риск маленького проекта: зависимость от внешнего API с квотами и лицензионными ограничениями.

Три индекса вместо одного — подарок для task-профилей: `coding_index` для кода, `agentic_index` для tool-use, `intelligence_index` как общий.

**Риск:** поле недокументировано на уровне контракта, семантика и частота обновления неизвестны, значения могут отставать от первоисточника. Митигация: считать снапшотным, а не эталонным; при исчезновении поля деградировать на ручной `overrides.json` (см. 12.2).

#### 5.1.3 Находка №2: `pricing.discount` существует — на другом эндпоинте

`GET /api/v1/models/{canonical_slug}/endpoints` отдаёт разбивку по провайдерам. Поля эндпоинта:

```
name, model_id, model_name, context_length, pricing, provider_name,
tag, quantization, max_completion_tokens, max_prompt_tokens,
supported_parameters, status, uptime_last_30m, uptime_last_5m,
uptime_last_1d, supports_implicit_caching, supports_voice_cloning,
latency_last_30m, throughput_last_30m
```

Внутри `pricing` здесь появляется подполе, которого нет в `/models`:

```json
"pricing": {"prompt": "0.0000014", "completion": "0.0000044",
            "input_cache_read": "0.00000026", "discount": 0}
```

Замер по выборке (70 моделей, 274 эндпоинта, 0 ошибок):

| Метрика | Значение |
|---|---|
| Эндпоинтов с ненулевым `discount` | **18 из 274 — 6.6%** |
| Диапазон значений | 0.1 … 0.65 (доля, не проценты) |
| Примеры | `openai/gpt-5.6-sol-pro` — 0.5 (OpenAI), `inclusionai/ling-3.0-flash` — 0.65 (Novita), `meituan/longcat-2.0` — 0.6 (AtlasCloud), `poolside/laguna-s-2.1` — 0.1 (Poolside) |

Экстраполяция на каталог: примерно **25–30 моделей** в любой момент имеют действующую скидку хотя бы у одного провайдера. Это достаточная плотность, чтобы дайджест не был пустым.

**Семантика `discount` — ПОДТВЕРЖДЕНА эмпирически (v1.1).** Скидка **уже применена** к полям `prompt` и `completion`. `discount: 0.70` означает «эта цена на 70% ниже базовой», а не множитель, который нужно применить.

Доказательство — сверка API с публичной коллекцией `/collections/discounted-models` по 12 моделям. У 11 цены совпали с точностью до знака: `google/gemini-3.7-flash` → `0.375/1.875` и там, и там при заявленных «75% off»; `inclusionai/ling-2.6-flash` → `0.01/0.03` при «90% off». Если бы скидку требовалось применять, числа расходились бы в 4 и 10 раз соответственно.

Практическое следствие: базовая цена восстанавливается как `price / (1 - discount)`, а не наоборот. Для Gemini 3.7 Flash: `0.375 / 0.25 = 1.50` — цена, к которой вернётся модель по окончании промо.

**Расчёт «было/стало» разрешён к реализации в PoC.** Ограничение из версии 1.0 снято.

#### 5.1.4 Находка №3 (v1.1): `/models` отдаёт цену дефолтного провайдера, а не лучшую

Двенадцатая модель из сверки — `z-ai/glm-5.2` — дала расхождение вдвое: API `/models` показал `0.966/3.036`, коллекция — `0.4186/1.316`. Разбор эндпоинтов объясняет причину.

GLM 5.2 обслуживают **30 провайдеров** с разбросом цены в **5.5 раза**:

| Провайдер | in / out (USD/1M) | discount | uptime_1d |
|---|---|---|---|
| Novita | 0.4186 / 1.3156 | 0.70 | 99.42 |
| **Baidu** | **0.4200 / 1.3200** | **0.70** | **99.92** |
| StreamLake | 0.5600 / 1.7600 | 0.60 | 99.84 |
| Decart | 0.6840 / 2.2800 | 0.43 | 99.46 |
| GMICloud | 0.7420 / 2.3320 | 0.47 | 99.14 |
| **Alibaba** | **0.9660 / 3.0360** | 0 | 99.51 |
| Z.AI, Fireworks, Together, … (13 шт.) | 1.4000 / 4.4000 | 0 | 94–99 |
| Alibaba (второй эндпоинт) | 2.3100 / 7.2600 | 0 | 99.91 |

`/models` вернул строку Alibaba. Коллекция показывает Novita. Разница для пользователя — **2.3× за идентичную модель**, причём у Baidu при этом uptime выше (99.92 против 99.51).

**Последствия для дизайна — существенные:**

1. **Обход `/endpoints` переходит из «желательного» в обязательное.** Логика, построенная на `/models`, систематически завышает цены и выдаёт неверный порядок в shortlist.
2. **Единица рекомендации — пара (модель, провайдер), а не модель.** Карточка обязана называть провайдера, иначе рекомендация неисполнима: пользователь не сможет воспроизвести названную цену.
3. **Появляется новый класс рекомендаций,** отсутствовавший в версии 1.0: «ты используешь правильную модель, но платишь втрое больше необходимого». Формализован как событие `cheaper_provider_available` (см. 11.3).
4. `/models` сохраняет роль дешёвого источника метаданных (индексы качества, контекст, модальности, tool-support) — но **не источника цены**.

**Оговорка о применимости.** Выбор конкретного провайдера в OpenRouter требует явного указания в запросе (провайдерские preferences). Рекомендация «переключись на Baidu» исполнима только для пользователя, который управляет этим параметром. Для Hermes-конфига это верно, что делает сигнал особенно ценным именно для нулевого пользователя. Для тех, кто полагается на дефолтный роутинг, сигнал носит информационный характер. Разделение фиксируется в карточке явно.

**Цена доступа:** ~403 запроса на полный обход (алиасы исключаются). При 10 параллельных потоках 70 моделей отработали без ошибок за единицы секунд. Полный обход раз в сутки из GitHub Actions — приемлемо. Rate limits для неавторизованного доступа не документированы; на первой неделе держим конкурентность 8–10 и логируем 429.

#### 5.1.5 Находка №4: latency и throughput отсутствуют

В выборке из 274 эндпоинтов:

| Поле | Заполнено |
|---|---|
| `uptime_last_5m` / `uptime_last_30m` / `uptime_last_1d` | есть, значения осмысленные (99.99, 100) |
| `latency_last_30m` | **0 из 274 (0%)** |
| `throughput_last_30m` | **0 из 274 (0%)** |

Поля объявлены в схеме, но пусты. Возможные причины: заполняются только для трафикогенерирующих эндпоинтов, требуют авторизации, или временно отключены.

**Вывод: метрика «скорость» из PoC и MVP-1 исключается полностью.** Не «доступна частично» — недоступна. Это честный отрицательный результат аудита, и его надо явно написать в README, потому что «а где latency?» — первый вопрос, который задаст любой технический читатель.

`uptime_last_1d` использовать можно, но как **фильтр надёжности** (отсекать <95%), не как ранжирующий фактор.

#### 5.1.6 Что НЕ проверено и намеренно отложено

- Страница `/rankings`, `/compare` — HTML, скрейпинг хрупок, семантика непрозрачна. Не берём как источник.
- Коллекция `/collections/discounted-models` — **не источник, но эталон для тестов.** HTML хрупок и в пайплайн не идёт, однако страница даёт готовый список моделей со скидками с указанием размера скидки. Используется как **валидационный набор**: если наш пайплайн выдаёт цену, отличную от коллекции, — ошибка на нашей стороне. Именно эта сверка выявила находку №3 и подтвердила семантику `discount`. Ручная сверка раз в неделю на 10 моделях — дешёвая и высокоценная проверка.
- Коллекции free-моделей — выводимо из `pricing.prompt == 0`, отдельный источник не нужен.
- Авторизованные эндпоинты (`/credits`, `/generation`) — дают факт собственного расхода. Это территория `bothub-llm-dashboard`, сюда не тащим.

|---|---|
| PoC | **Да, полностью.** Цена (по эндпоинтам), контекст, три индекса качества, модальности, tool-support, скидки, uptime, провайдеры |
| MVP-1 | **Да.** Плюс накопленная собственная история для дельт |

#### 5.1.8 Data API — авторизованный слой (обнаружен в v1.2, проверен в v1.3)

Отдельное семейство эндпоинтов, документированное в cookbook и не пересекающееся с публичным `/models`. **Гейт: любой валидный OpenRouter API-ключ** (тот же, что для inference). Лимиты: **30 запросов/минуту на ключ, 500/сутки на аккаунт**.

**Лицензия — ключевой пункт.** Данные под **CC BY 4.0** с явным разрешением копировать, перераспределять и строить поверх, в том числе коммерчески, при указании атрибуции. Требуемая строка:

> `Source: OpenRouter (openrouter.ai/rankings), as of <meta.as_of>.`

Для бенчмарков атрибуция указывает первоисточник: `Source: Artificial Analysis (artificialanalysis.ai) via OpenRouter (openrouter.ai/rankings).`

Это **снимает главное возражение против публикации чужих бенчмарков** — то самое, ради которого в версии 1.0 Artificial Analysis выносился в validation-only.

#### Состав

| Эндпоинт | Что даёт | Ценность для продукта |
|---|---|---|
| `/api/v1/datasets/rankings-daily` | топ-50 моделей по токенам за день + агрегат `other`; поля `date`, `model_permaslug`, `total_tokens`; история **с 2025-01-01**, окно до 366 дней | **Высокая.** Закрывает «топ-N по объёму» и даёт готовую историю без ожидания накопления |
| `/api/v1/benchmarks` | AA-индексы, Design Arena ELO, собственные бенчмарки OpenRouter; фильтры `source`, `task_type` (`coding`/`intelligence`/`agentic`/`search`) | Средняя. Дублирует то, что уже есть в `/models`, но с атрибуцией и фильтрами |
| `/api/v1/classifications/task` | доли трафика по типам задач (`code:general_impl`, `agent:web_search`…) + топ-модели в каждой | **Высокая для валидации task-профилей.** Показывает, какие профили реально существуют, а не выдуманы нами |
| `/api/v1/datasets/app-rankings` | топ приложений по токенам | Низкая. Не про выбор модели |
| `session-cost` | стоимость типовой сессии coding-агента по длине сессии | **Потенциально высокая** — см. ниже |

#### Пересмотр позиции по `cost per task`

В версии 1.0 было записано: готового сигнала нет, не вычислять. **Это утверждение требует уточнения.**

В ответе `source=openrouter` для поисковых бенчмарков присутствуют поля:

```
"primary_score": 0.7199,
"total_tasks": 100,
"avg_cost_per_task": 0.031,
"avg_latency_per_task_ms": 45210
```

То есть **`avg_cost_per_task` и `avg_latency_per_task` существуют как прямые измерения** — но только для узкого набора собственных поисковых бенчмарков OpenRouter (`search_browsecomp`, `search_hle`, `search_dsqa`, `search_widesearch`) плюс классические GPQA / tau-bench.

Честная переклассификация:

| | Версия 1.0 | Версия 1.2 |
|---|---|---|
| `cost per task` (универсально, любая задача) | proxy only | **proxy only** — не изменилось |
| `cost per task` на поисковых/агентных бенчмарках | не рассматривалось | **directly available**, авторизованно |
| `latency` | not realistically available | **directly available для бенчмарков**; по-прежнему отсутствует по эндпоинтам |

Практический вывод: продукт **по-прежнему не вычисляет** cost per task для произвольной пользовательской задачи — это невозможно без телеметрии. Но у нас появляется **эталонная точка**: реальная стоимость выполнения стандартизованной агентной задачи. Это качественно лучше, чем blended price с допущением 3:1, и напрямую отвечает на вопрос «сколько мне будет стоить прогнать эту модель на реальной работе».

Отдельно ценен `avg_latency_per_task_ms`: латентность, которую мы вычеркнули из-за пустых полей в `/endpoints`, здесь **есть** — измеренная на реальных задачах, а не как мгновенный показатель провайдера. Это более осмысленная метрика.

#### Решение по стадиям

| Стадия | Использование Data API |
|---|---|
| **PoC** | **Не использовать.** Требует ключа → секрет в CI, лимиты, ещё одна точка отказа. Публичного `/models` + `/endpoints` достаточно, и это ценно само по себе: продукт работает без авторизации |
| **MVP-1** | **`rankings-daily` — первый кандидат на подключение.** Даёт объём как критерий гейта и историю с 2025-01-01, то есть мгновенный ответ на H2 («как часто меняются цены») без ожидания двух недель |
| **MVP-2** | `classifications/task` для валидации профилей; `benchmarks` с `avg_cost_per_task` — если подтвердится спрос на «сколько это реально стоит» |

#### 5.1.9 Reasoning effort — скрытое измерение цены (v1.3)

**Поле `reasoning` присутствует у 286 из 415 моделей** и описывает управление глубиной рассуждений:

| Подполе | Заполнено | Значения |
|---|---|---|
| `mandatory` | 286 | `true` у 89, `false` у 197 |
| `supported_efforts` | 137 | наборы из 2–6 уровней |
| `default_effort` | 137 | `medium` 71, `high` 47, `max`/`xhigh` 8, `minimal` 8 |
| `default_enabled` | 119 | |

Уровней не два, а до шести. Самые частые наборы:

| Набор | Моделей |
|---|---|
| high, medium, low, minimal | 19 |
| max, xhigh, high, medium, low | 16 |
| high, medium, low | 15 |
| max, xhigh, high, medium, low, none | 13 |

Примеры:

```
openai/gpt-5.6-luna     mandatory=false  [max,xhigh,high,medium,low,none]  default=medium
google/gemini-3.7-flash mandatory=true   [high,medium,low]                 default=medium
z-ai/glm-5.3            mandatory=true   [max,high,low]                    default=max
```

**Ключевая находка: reasoning-токены тарифицируются как обычный output.** У 30 моделей есть `pricing.internal_reasoning`, и он равен цене completion один к одному:

```
gemini-3.7-flash    completion = 1.875    internal_reasoning = 1.875
gemini-3.5-flash    completion = 9.000    internal_reasoning = 9.000
```

Отсюда следует вывод, важный для корректности всего продукта: **переключение effort не меняет цену за токен, но меняет количество генерируемых токенов — в разы.** Реальная стоимость растёт невидимо: она не в `pricing`, а в объёме генерации, которого мы не наблюдаем.

**Следствие для текущих расчётов.** Весь `blended_price` в спеке — это цена **при дефолтном effort**, и дефолты у моделей разные. Сравнение `glm-5.3` (default `max`, reasoning обязателен) с `gemini-3.7-flash` (default `medium`) по одной ценовой колонке некорректно: мы уже сравниваем разные режимы, не помечая этого.

**Что делать — разделение по стадиям.**

*PoC (стоит ноль, обязательно):*

- выводить в карточке `default_effort` и `mandatory`;
- фильтр для профиля `bulk`: `mandatory=true` — **дисквалификация**. Платить за размышления при массовой генерации бессмысленно;
- дисклеймер в `report.md` и на странице: «цена приведена для дефолтного reasoning effort; при `high` фактический расход выше»;
- поле `default_effort` в снапшот — чтобы диффы ловили его изменение.

*MVP-2 (требует отдельной работы):*

- колонка «цена при high» — но это **замер**, а не вычисление: нужен прогон фиксированного промпта через API на каждом уровне effort с подсчётом фактических токенов. Это стоит денег и времени, в неделю прототипа не помещается.

Откладывать целиком нельзя: без пометки об effort рекомендации уже сейчас частично вводят в заблуждение. Метки в PoC закрывают честность, замеры в MVP-2 закрывают точность.

### 5.2 Artificial Analysis — вторичный источник

Оценка изменена по итогам находки 5.1.2.

| Аспект | Оценка |
|---|---|
| Публично / бесплатно | Веб-интерфейс с бенчмарками, intelligence index, ценами. Просмотр свободен |
| API | Существует, требует ключ, есть бесплатный tier с ограничениями |
| Платное / коммерческое | Расширенный доступ, историчность, выгрузки — по коммерческим условиям |
| Redistribution | **Главный риск.** Публикация чужих бенчмарков на своём сайте — вопрос лицензии, не техники. Для публичного репозитория в портфеле это репутационно значимо |
| Cost per task | Как готовый универсальный сигнал — **не рассчитывать на него.** Существует blended price (взвешенная смесь input/output), но это не «стоимость задачи» |
| Операционная зависимость | Ключ в secrets, квоты, отказ ломает пайплайн |

**Решение:**

- **PoC:** не используется. Совсем.
- **MVP-1:** не используется. Индексы берутся из OpenRouter.
- **MVP-2:** опционально, **только как validation-only** — ручная сверка «совпадает ли индекс внутри OpenRouter с первоисточником». Не встраивать в пайплайн, не публиковать значения как свои.

Это снимает вопрос лицензирования: мы публикуем то, что OpenRouter сам отдаёт в своём публичном API, со ссылкой на происхождение.

### 5.3 Третий источник

**Не нужен.** Единственный кандидат, который реально снизил бы риск, — независимый источник цен для перекрёстной проверки (прайс-листы вендоров напрямую). Но польза наступает только в сценарии «OpenRouter систематически врёт», вероятность которого низка, а стоимость поддержки N вендорских парсеров высока.

Единственный источник, который войдёт позже и по другой причине, — **собственная история**. Она не внешняя и появляется бесплатно с первого дня.

| **cost per task** (GPQA / tau-bench / search) | **paid-gated, ПРОВЕРЕНО** | `avg_cost_per_task`, 99/100 моделей на GPQA (v1.3) |
| **latency на задаче** | **paid-gated, частично** | `avg_latency_per_task_ms` — только поисковые бенчмарки, 4 модели (v1.3) |
| объём токенов по моделям | **paid-gated, ПРОВЕРЕНО** | `rankings-daily`, 59 моделей/неделю, история с 2025-01-01, CC BY 4.0 |
| доли трафика по типам задач | **paid-gated, ПРОВЕРЕНО** | `/api/v1/classifications/task`, окно 7d |
| **design_arena rank / elo / win_rate** | **directly available** | 158 моделей, 25 категорий, бесплатно |
| число категорий design_arena | **derivable** | критерий G6 |
| reasoning efforts / default / mandatory | **directly available** | 286 моделей (efforts у 137) |
| цена reasoning-токенов | **directly available** | `pricing.internal_reasoning`, 30 моделей — равна цене output |
| **расход токенов при разном effort** | **not realistically available** | требует собственных прогонов через API (MVP-2) |
| качество на конкретной задаче | **proxy only** | coding_index / agentic_index как прокси |
| надёжность провайдера | **proxy only** | uptime как прокси |
| историческая динамика цен | **paid-gated** | у внешних источников; у нас — накапливаем сами |

**Про `cost per task` отдельно, как требует спека.** Готового сигнала нет ни в одном рассмотренном источнике. Честная реконструкция требует знать распределение длин промптов и ответов, долю кеш-попаданий, объём reasoning-токенов и число ретраев — то есть телеметрию, которой у нас нет.

Позиция: **не вычислять cost per task.** Вместо этого использовать явно помеченный прокси — **blended price при фиксированном соотношении**, с открытым указанием допущения прямо в интерфейсе:

> Цена за 1M токенов при соотношении 3:1 (вход:выход). Ваш профиль нагрузки может отличаться.

Соотношение 3:1 — консервативный дефолт для чат/агентных нагрузок. Оно задаётся в конфиге и настраивается на уровне task-профиля (для «дешёвой массовой генерации» разумнее 1:3 — короткий промпт, длинный ответ). Явное допущение честнее, чем красивое число, полученное из воздуха.

## 7. Recommendation logic options

### 7.0 Scope gate — сокращение пространства до обхода эндпоинтов

**Мотивация.** Каталог содержит 415 моделей, но реальный выбор крутится вокруг нескольких десятков. Обходить эндпоинты для всех — платить 400+ запросов за данные, которые в отчёт не попадут. Гейт применяется **до** обхода `/endpoints`, работает на бесплатном `/models` и стоит ноль запросов.

Это не оптимизация ради скорости. Гейт меняет три вещи: снимает риск rate-limiting, ужимает снапшот впятеро и — главное — даёт набор, который **можно проверить глазами**. 388 моделей проверить нельзя, 86 можно.

#### Правила

**Шаг 1 — вычесть заведомо неподходящее** (бесплатно, без потерь):

- алиасы (`alias_target != null`) — 12 моделей;
- non-text output: video, image, audio (`output_modalities` вне `{text}`);
- voice-модели (`supported_voices` непусто).

`415 → 403 → 388`.

**Шаг 2 — гейт.** Модель проходит, если выполнено **хотя бы одно** из четырёх:

| # | Критерий | Смысл |
|---|---|---|
| **G1** | топ-20 по любому из `intelligence_index`, `coding_index`, `agentic_index` | сильнейшие по качеству |
| **G2** | топ-20 по `value_ratio` = индекс ÷ blended-цена, по любому из трёх индексов | **дешёвые находки** |
| **G3** | `rank ≤ 7` в любой категории `benchmarks.design_arena` | сильные в прикладной нише |
| **G4** | бесплатная (`pricing.prompt == 0`) | value = ∞, ценовые критерии на них ломаются |
| **G6** | **участие** в ≥6 категориях `design_arena` **И** возраст < 180 дней | протестирована всерьёз, независимо от места |

**Результат: 388 → 77 моделей (по `canonical_slug`), экономия ~80% запросов.**

#### G6 — участие в бенчмарках как отдельный сигнал (добавлен в v1.3)

G1–G3 учитывают **место** в бенчмарке. Ни один не учитывает **факт участия**, а это независимый сигнал: попадание в Design Arena означает, что модель прошла достаточно head-to-head битв, чтобы получить ELO. Это порог внимания сообщества, не зависящий от ранга.

Провал обнаружился на `tencent/hy3` — **второй по объёму модели на всём OpenRouter** (9.83T токенов/неделю):

```
tencent/hy3 — design_arena, 6 категорий:
   3d              rank=42      dataviz       rank=74
   codecategories  rank=52      uicomponent   rank=60
   gamedev         rank=62      website       rank=58
```

Модель **есть** в шести категориях, но лучший ранг — 42, при пороге G3 ≤ 7. AA-индексы у неё отсутствуют: они есть у `tencent/hy3-preview`, у релизной версии их нет. Модель проваливается в щель между критериями.

Ослабление порога G3 не помогает: `rank ≤ 7` даёт 44 модели, `≤ 15` — 57, а ранг 42 требует порога, впускающего половину каталога. **Место — неверный параметр; правильный — количество категорий.**

Распределение имеет естественный обрыв:

| Категорий DA | Моделей |
|---|---|
| 0 | 245 |
| 1–5 | 26 |
| **6** | **26** |
| 7 | 18 |
| 8 | 30 |
| 12–21 | 39 |

Шесть — граница «модель протестировали всерьёз».

**Возрастной фильтр обязателен.** Чистый критерий «≥6 категорий» добавляет 65 моделей и удваивает набор — в основном за счёт устаревших (`claude-opus-4`, `deepseek-chat`, `deepseek-r1-0528`): накопленные битвы никуда не деваются, и старые модели набирают категории просто со временем. Отсечка `created` < 180 дней оставляет **15 добавленных**, и все они живые:

| Модель | категорий | ранг | ELO | возраст |
|---|---|---|---|---|
| `qwen/qwen3.7-max` | 16 | 8 | 1321 | 90д |
| `x-ai/grok-4.3` | 21 | 9 | 1221 | 111д |
| `xiaomi/mimo-v2.5-pro` | 8 | 15 | 1303 | 119д |
| `deepseek/deepseek-v4-pro` | 11 | 16 | 1307 | 118д |
| **`tencent/hy3`** | **6** | **42** | **1227** | **44д** |
| `openai/gpt-5.3-codex` | 13 | 24 | 1200 | 176д |
| … ещё 9 | | | | |

Рассматривался вариант «≥6 категорий И (ELO ≥ 1250 ИЛИ моложе 180д)» — даёт 72 добавленных, слишком много. Чистый возрастной фильтр точнее.

**G6 покрывает 173 модели без AA-индексов частично, но не полностью** — у 173 моделей нет вообще никаких бенчмарков, и туда G6 не дотягивается. Это остаётся зоной ответственности G5 (объём), доступного только через Data API.

#### Почему именно четыре критерия

G2 и G4 добавлены не для симметрии — без них гейт **теряет то, ради чего продукт существует**.

Проверка на данных: `openai/gpt-5.6-luna` — лидер по ценности во всём каталоге (`coding_index / $` = 317, вдвое выше второго места). При этом он на **26-м** месте по coding, **33-м** по intelligence и **отсутствует** в Design Arena. Гейт из одних только G1+G3 его выбрасывает. Через G2 он проходит на 20-й, 20-й и 13-й позициях.

Это структурная закономерность, а не единичный случай: дешёвые модели по определению не попадают в топ по абсолютному качеству, а именно они и есть искомая находка. Гейт, отбирающий по качеству, систематически слеп к главному классу рекомендаций.

Вклад критериев в итоговый набор:

| Через что прошли | Моделей |
|---|---|
| AA-индексы (G1 и/или G2) | 51 |
| **только** Design Arena rank (G3) | 18 |
| **только** бесплатные (G4) | 17 |
| **только** участие в бенчмарках (G6) | **15** |

G3, G4 и G6 не дублируют G1/G2 — 50 моделей из 77 проходят исключительно через них.

#### Валидация гейта

Приёмочный тест: **полный прогон против урезанного**, сравнение по попаданию в топ-10 профиля `code` по ценности.

| Конфигурация | Моделей | Экономия | Топ-10 сохранён |
|---|---|---|---|
| G1(20) + G3(7) | 48 | 88% | 8/10 |
| G1(20) + G2(20) + G3(7) | 69 | 83% | 9/10 |
| G1(20) + G2(20) + G3(7) + G4 | 86* | 78% | 9/10 |
| G1(25) + G2(25) + G3(7) | 77 | 81% | 9/10 |
| G1(15) + G2(15) + G3(5) | 62 | 85% | 9/10 |
| **G1–G4 + G6 (финальная, v1.3)** | **77** | **~80%** | **9/10 + `hy3`** |

\* Расхождение 86 против 60 для одной конфигурации — следствие разных ключей сопоставления (`id` против `canonical_slug`). См. открытый вопрос №18.

Выбрана конфигурация с G4: те же 9/10 при чуть большем наборе, но бесплатные модели важны для профиля `bulk`, где они часто оказываются рабочим ответом.

Единственная потеря в топ-10 — `openai/gpt-5.4`, который ни при каком пороге не попал бы в отчёт (8-е место по ценности, доминируется по всем осям).

#### Что фиксируется в артефактах

- каждая модель в снапшоте получает `gate_reason` — список сработавших критериев (`["q:coding", "v:agentic", "da:3"]`);
- отсеянные модели пишутся в `data/gate_rejected.json` — только slug и причина, без обхода эндпоинтов;
- в `report.md` — строка «рассмотрено 86 из 415 моделей», со ссылкой на правила.

#### Обязательная процедура первой недели

Список `gate_rejected` **просматривается глазами ежедневно первые 7 дней**. Гейт — единственное место в пайплайне, где ошибка невидима: модель, не прошедшая отбор, просто не появится, и никакая метрика об этом не сообщит. Это порождает четвёртый тип обратной связи, которого не было в версии 1.1:

| Тип | Что означает |
|---|---|
| модель в отчёте, оказалась полезной | логика работает |
| модель в отчёте, оказалась мусором | пороги статусов надо править |
| прошла гейт, но в отчёт не попала | нормально, отсекла логика |
| **отсеяна гейтом, а была нужна** | **гейт врёт — правило требует пересмотра** |

#### G5 — критерий по объёму токенов (проверен в v1.3)

Изначальная формулировка гипотезы включала «топ-20 по объёму». **Через публичный API недоступно:** в `/models` нет полей usage, `?order=top-weekly` принимается (HTTP 200), но игнорируется.

Через **Data API** доступно и **проверено** (5.1.8): `rankings-daily` за 7 дней даёт 59 уникальных моделей, сопоставление с `canonical_slug` — 59 из 59 после отсечения суффиксов `:free` / `:batch`.

**Ключевой результат проверки: объём не дублирует остальные критерии.** Из топ-20 по объёму **4 модели не проходят гейт v1.2**:

| Модель | Объём за неделю | Почему не прошла |
|---|---|---|
| `tencent/hy3` | **9.83T (2-е место)** | нет AA-индексов, нет в Design Arena |
| `deepseek/deepseek-v4-pro-0423` | 2.57T | не в топ-20 ни по качеству, ни по ценности |
| `stepfun/step-3.7-flash` | 0.86T | нет данных бенчмарков |
| `google/gemini-3-flash-preview` | 0.82T | вытеснена свежими версиями |

`tencent/hy3` — **вторая по объёму модель на всём OpenRouter**, 9.83T токенов в неделю, и текущий гейт её теряет. Это ровно тот провал, о котором говорит процедура ежедневного просмотра `gate_rejected`. Объём ловит модели, у которых нет бенчмарков, но есть массовое реальное использование — независимое измерение, не выводимое из качества.

**Формулировка G5:** модель в топ-30 по `total_tokens` за trailing 7 дней (Data API, `rankings-daily`).

Влияние на размер набора:

| Конфигурация | Моделей |
|---|---|
| G1(20)+G2(20)+G3+G4 — гейт v1.2 | 60* |
| **+ G5(top-30 объём)** | **68** |
| G1(10)+G2(10)+G3+G4+G5(top-30) | **63** |

\* Цифра 60 против 86 в таблице выше — разные ключи сопоставления (`canonical_slug` против `id`); на выводы не влияет, но при реализации ключ должен быть **один** — `canonical_slug`. Это ловушка, стоящая отдельной проверки в приёмочном тесте.

**Вывод:** G5 добавляет 8 моделей и закрывает слепое пятно. Ужесточение G1/G2 с 20 до 10 при наличии G5 даёт набор в 63 модели — то есть **объём позволяет резать пороги качества почти вдвое без потери покрытия**, что подтверждает исходную интуицию.

**Решение по стадиям:** G5 требует ключа → в PoC не входит. Первое, что подключается в MVP-1. До этого `design_arena.rank` работает частичной заменой.

### 7.1 Эвристический shortlist (рекомендуется для PoC)

Работает при минимуме данных, полностью объясним, отлаживается глазами.

**Шаг 1 — фильтры пригодности.** Отсекаем:
- алиасы (`alias_target != null`) — 12 моделей;
- модальности вне профиля;
- отсутствие `tools`, если профиль агентный;
- `context` ниже порога профиля;
- `uptime_1d < 95%` у всех эндпоинтов;
- отсутствие индекса качества → в отдельную корзину «нет данных», не в мусор.

**Шаг 2 — порог достаточного качества.** Для каждого task-профиля задан минимальный индекс `Q_min`. Не «лучшая модель», а **«достаточно хорошая»** — это принципиально: продукт про экономию, а не про максимизацию качества.

**Шаг 3 — сортировка выживших по `blended_price` возрастающе.**

**Шаг 4 — присвоение статусов** (раздел 7.4).

Пороги `Q_min` на старте калибруются вручную по 149 моделям с индексом и фиксируются в конфиге как явные, обсуждаемые числа — не как магия в коде.

### 7.2 Pareto / frontier

Строим фронт недоминируемых по паре (цена ↓, интеллект ↑). Математически честно, красиво выглядит, объясняется одной фразой: «нет модели дешевле и умнее одновременно».

Проблемы:
- фронт легко даёт 15–25 моделей — это не shortlist;
- knee point может отсутствовать: при ~149 точках, разбросанных по трём порядкам цены, перегиб часто визуально неоднозначен;
- фронт нестабилен: одна новая дешёвая модель перестраивает всю картину, и рекомендации «прыгают» день ото дня, что разрушает доверие;
- требует графика, чтобы объяснить, а график в PoC мы решили не делать.

**Вывод: Pareto — не логика PoC.** В MVP-1 входит как *фильтр-обогатитель*: `pareto_rank` вычисляется и показывается как бейдж «на фронте эффективности», но сортировка остаётся эвристической. Knee point как основа рекомендаций — **не делаем никогда без эмпирического подтверждения, что перегиб устойчив хотя бы 2 недели подряд**.

### 7.3 Fallback при отсутствии чёткого перегиба

Поскольку исходить надо из того, что перегиба нет:

| Подход | Суть | Вердикт |
|---|---|---|
| **Value-per-cost threshold** | `intelligence / blended_price`, отсечка по перцентилю | **PoC.** Одно число, объяснимо, устойчиво |
| **Zone-based heuristics** | 3 ценовые зоны (дешёвая / средняя / премиум), лучший по качеству в каждой | **PoC.** Даёт структуру карточкам, защищает от «всё дешёвое» |
| **Tolerance bands** | полоса ±X% вокруг фронта вместо строгого фронта | MVP-1 |
| **Dominance with margins** | доминирование считается только при отрыве >10% по обеим осям | MVP-1. Прямое лекарство от дрожания рекомендаций |
| **Parallel shift of frontier** | сдвиг фронта, взять первую пересечённую точку | MVP-2. Требует стабильного фронта |
| **Piecewise business rules** | ручные правила под конкретные задачи | MVP-2, только под подтверждённый спрос |

Комбинация для PoC: **зоны + value_ratio + порог качества**. Три простых механизма, каждый объясняется одним предложением.

### 7.4 Labels and taxonomy

Четыре статуса. Каждый — с явными сигналами и явным действием.

---

**🟢 `This is your default` — «Это твой рабочий вариант»**

Сигналы: качество ≥ `Q_min` профиля · цена в нижних 50% среди прошедших порог · uptime ≥ 99% · поддержка tools (для агентных профилей) · присутствует в shortlist ≥ 3 дня подряд (с MVP-1).

Действие: ничего не делай, если уже используешь. Иначе — ставь.

Ограничение: **ровно одна модель на профиль.** Два дефолта — это не дефолт.

---

**🔵 `Good enough and cheaper` — «Не хуже по сути, но дешевле»**

Сигналы: качество ≥ `Q_min` (допустимо ниже дефолта, но не более чем на 5 пунктов индекса) · цена **минимум на 30% ниже** дефолта · uptime ≥ 98%.

Действие: кандидат на переключение для массовых задач.

Порог 30% — не косметика: переключение имеет цену (тестирование, риск регрессии), и экономия 10% её не окупает.

---

**🟡 `Big discount, but not my safe default` — «Большая скидка, но не для основной работы»**

Сигналы: `discount_max ≥ 0.3` · И хотя бы одно из: качество < `Q_min`, uptime < 98%, нет tools, скидка у одного малоизвестного провайдера, модель моложе 14 дней.

Действие: посмотреть, попробовать на некритичном, не ставить дефолтом.

Этот статус — прямой ответ на риск «дешёвое ≠ подходящее». Данные его подтверждают: в выборке скидка 0.65 была у `inclusionai/ling-3.0-flash` через Novita — то есть максимальные скидки концентрируются не у флагманов.

---

**🟠 `Same model, cheaper provider` — «Та же модель, но ты переплачиваешь»** *(добавлено в v1.1)*

Сигналы: `overpay_ratio ≥ 1.5` (дефолтный роутинг дороже лучшего провайдера в 1.5+ раза) · uptime лучшего провайдера ≥ 99% · модель уже в shortlist или используется пользователем.

Действие: не менять модель — **закрепить провайдера** в настройках запроса.

Пример из данных: GLM 5.2 через дефолтный роутинг — $1.72/1M (Alibaba), через Baidu — $0.64/1M при uptime 99.92%. Переплата 2.7× за идентичную модель.

Это самый «дешёвый» для пользователя статус: не требует тестирования на регрессию, потому что модель не меняется. Риск ограничен надёжностью провайдера, которую мы измеряем.

---

**⚪ `Probably not worth switching` — «Скорее всего, менять не стоит»**

Сигналы: доминируется дефолтом по обеим осям · или экономия < 30% · или качество ниже порога без ценового преимущества.

Действие: явное «нет». Показывается свёрнутым списком, 1 строка на модель.

Этот статус существует ради снижения тревоги: пользователь должен видеть, что альтернативы **рассмотрены и отклонены**, иначе он пойдёт проверять руками — и продукт не сработал.

---

**🔴 `Discount vanished — your cost went up` — «Скидка кончилась, ты стал платить больше»** *(MVP-1)*

Сигналы: модель была в shortlist со скидкой · скидка ушла или упала более чем вдвое · рост эффективной цены ≥ 25%.

Действие: пересмотреть. **Единственный статус, требующий немедленной реакции**, и единственный, достойный push-уведомления.

---

### 7.5 Task-профили

Четыре фиксированных профиля в PoC, зашиты в конфиг:

| Профиль | Метрика качества | Q_min | Мин. контекст | tools | Соотношение in:out |
|---|---|---|---|---|---|
| `chat` — быстрый ассистент | intelligence | средний | 32k | нет | 3:1 |
| `code` — код | **coding_index** | высокий | 128k | да | 3:1 |
| `longdoc` — документы | intelligence | средний | **≥ 200k** | нет | 10:1 |
| `bulk` — массовая генерация | intelligence | **низкий** | 16k | нет | **1:3** |

Дополнительный фильтр для `bulk` (v1.3): **`reasoning.mandatory = true` — дисквалификация.** Модель, которая не умеет выключать рассуждения, при массовой генерации сжигает деньги на невидимые reasoning-токены, тарифицируемые как output.

Пятый профиль под карточки маркетплейсов **не добавляем**: он математически совпадает с `bulk` (короткий промпт → длинный текст → важна дешевизна, не гениальность). Добавлять дубль ради резонанса с аудиторией, которая, по гипотезе H6, продуктом не воспользуется, — плохой размен.

`agentic_index` в PoC не используется как основной, но выводится в карточке — понадобится для Hermes Auto-Config.

**Проверка профилей реальным спросом (v1.3).** `/api/v1/classifications/task` даёт фактическую структуру трафика OpenRouter за 7 дней:

| Макро-категория | доля запросов | **доля токенов** |
|---|---|---|
| General | 0.569 | 0.256 |
| Data | 0.188 | 0.058 |
| **Agent** | 0.136 | **0.347** |
| **Code** | 0.108 | **0.339** |

Code и Agent — 24% запросов, но **69% токенов**, то есть примерно 69% денег. Выбор профилей `code` и `agentic` как приоритетных подтверждён внешними данными, а не интуицией.

Одновременно данные показывают пробел: **Data Extraction — 13.7% запросов, третья по величине задача**, и она не покрыта ни одним из четырёх профилей. Кандидат в пятый профиль наравне с `agentic` — но по токенам (4.4%) это дешёвый сегмент, поэтому приоритет ниже. Зафиксировано в открытых вопросах.

## 8. Staged roadmap

### 8.1 PoC — «полочка на одного»

**Срок:** ~5 рабочих дней, ценность включается на 8–10 день.
**Гипотезы:** H1, H4, H5.

**Критерий успеха (фальсифицируемый):**
> За 14 дней с момента запуска автор ≥1 раз изменил модель в своём Hermes `config.yaml` на основании артефакта и по итогам не откатил изменение.

**Критерий провала:** ноль изменений, либо изменение с откатом, либо «я и так это знал» на каждой карточке.

**Данные:** только публичные `/models` + `/endpoints` OpenRouter, без авторизации. Data API — не в PoC (раздел 5.1.8).

**Scope gate (раздел 7.0):** 415 → ~86 моделей до обхода эндпоинтов. Список отсеянных просматривается глазами ежедневно первые 7 дней.

**UI:** одна статическая страница. Четыре секции по task-профилям, в каждой 4–6 карточек. Никаких графиков, фильтров, поиска, таблицы на 400 строк.

Карточка содержит: имя модели · статус-бейдж · цена USD/1M (с пометкой о допущении 3:1) · индекс качества · контекст · **одна строка «почему»** · бейдж скидки при наличии.

Строка «почему» — самый важный элемент интерфейса. Если её нельзя сформулировать одним предложением, логика слишком сложна для PoC.

**Артефакты:** `data/snapshots/YYYY-MM-DD.json`, `data/latest.json`, `shortlist.json`, `report.md`, `index.html`.

**Что собираем как feedback:** личный лог в `NOTES.md` — дата, что показал артефакт, что сделал, что оказалось бесполезным шумом. Свободная форма, честно, без причёсывания. Этот файл потом станет скелетом статьи на Хабр.

**Чего в PoC нет:** истории (накапливается, но не используется), Telegram, графиков, дельт, алертов, персонализации, поиска.

---

### 8.2 MVP-1 — «что изменилось»

**Условие входа:** H1 подтверждена. Если нет — не начинать, а разбираться почему.
**Срок:** ~1 неделя после ≥10 дней накопленной истории.
**Гипотезы:** H2, H3, H6.

Добавляется:

1. **Change detection** — сравнение с предыдущим снапшотом: цена ↑/↓, скидка появилась/**исчезла**, модель добавлена/удалена, индекс изменился.
2. **Секция «Что изменилось» вверху страницы.** Выше shortlist — потому что H3 говорит, что это ценнее.
3. **`changes.json`** как отдельный артефакт.
4. **`pareto_rank`** как бейдж (не как сортировка).
5. **Dominance with margins** — против дрожания рекомендаций.
6. **Telegram-дайджест** — только если за первые 10 дней автор обнаружил, что забывает заходить на сайт. Реализация: канал, отправка из Actions, bot token + chat id в secrets. Без диалогового бота, без webhook, без хостинга.
7. **Data API с ключом** (5.1.8, проверен): `rankings-daily` как критерий **G5** — закрывает слепое пятно гейта (`tencent/hy3`, 2-е место по объёму, сейчас теряется). Плюс готовая история от 2025-01-01: даёт ответ на H2 сразу, без ожидания накопления. Требует отдельного ключа и секрета в CI.
8. **Первый показ сегменту 2.** Ссылка + один вопрос: «есть ли здесь что-то, из-за чего вы бы что-то изменили?» Ожидаем «нет». Записываем ответы дословно.

**Критерий успеха:** ≥40% дней содержат хотя бы одно изменение, которое автор оценил как «стоило знать».

---

### 8.3 MVP-2 — «только подтверждённое»

**Условие входа:** H2 и H3 подтверждены; есть ≥1 внешний человек, который вернулся сам.

Кандидаты, в порядке вероятности:

| Что | Условие включения |
|---|---|
| **Hermes config advisor** | Автор ≥3 раза менял конфиг вручную по рекомендации. Ценность = замыкание цикла «рекомендация → исполнимый diff». Главный кандидат |
| Watchlist «следить за моими моделями» | Автор заметил, что фильтрует дайджест глазами |
| Персональные алерты | Появился ≥1 внешний регулярный пользователь. **Первая точка, где ломается static-first** |
| Настраиваемое соотношение in:out | Автор понял, что дефолт 3:1 систематически врёт |
| **Замер цены при разных reasoning effort** | Автор упёрся в то, что `high` меняет счёт непредсказуемо. Требует прогонов через API за свои деньги |
| Расширенные task-правила | Появился спрос на профиль, не покрытый четырьмя |
| Валидация через Artificial Analysis | Возникло подозрение, что индексы внутри OpenRouter устарели |

**Явно НЕ делаем в MVP-2:** аккаунты, авторизацию, БД, мультитенантность, платные тарифы, real-time.

## 9. UX / delivery options

### Принцип

Интерфейс **decision-support**, не BI. Метрика качества интерфейса: **время от открытия до решения**. Целевое — под 60 секунд. Всё, что его увеличивает, — вред, даже если красиво.

### По стадиям

| Стадия | Главная сущность | Сценарий | График? |
|---|---|---|---|
| PoC | **карточка модели** | открыл → выбрал профиль → прочёл 4 карточки → решил | **Нет** |
| MVP-1 | **строка изменения** | открыл → прочёл «что изменилось» → при необходимости пошёл в карточки | Опционально |
| MVP-2 | **алерт-сообщение** | получил push → одно решение | Нет |

### Когда график добавляет ценность, а когда это декорация

**Декорация (PoC):** scatter cost×intelligence на 149 точках. Выглядит убедительно, читается плохо, решение не ускоряет. Пользователь всё равно смотрит на 4 карточки. Классический случай, когда график продаёт продукт автору, а не помогает пользователю.

**Ценность (MVP-1, условно):** маленький спарклайн истории цены **внутри карточки**. Отвечает на реальный вопрос «это разовая скидка или тренд». Занимает 40×12 пикселей, не требует легенды.

**Ценность (MVP-2, если):** scatter — только если появится обучающий сценарий «покажи мне всё поле, я хочу разобраться сам». Это уже другой JTBD.

Позиция: **в PoC графика нет.** H5 проверяет это явно.

### Каналы доставки

| Канал | Плюсы | Минусы | Стадия |
|---|---|---|---|
| **Статический сайт** | ноль инфраструктуры, ссылка в портфолио, работает как витрина для работодателя | pull-модель, легко забыть | **PoC** |
| **`report.md` в репо** | читается прямо в GitHub, версионируется, diff между днями бесплатно | не для внешних | **PoC** |
| **Telegram-дайджест** | push, привычный канал | ещё один шаг в пайплайне, риск стать шумом | MVP-1 условно |
| **Telegram-алерты** | максимальная ценность на «скидка пропала» | персонализация ломает static-first | MVP-2 |

Для карьерной цели **сайт обязателен** независимо от продуктовой полезности: живая ссылка — часть артефакта. Но приоритет внимания в продуктовом смысле — у `report.md`, потому что его диффы в git и есть история продукта.

## 10. Technical architecture

### Схема

```
GitHub Actions (cron, 1×/сутки)
   │
   ├─ fetch:     /api/v1/models            → 1 запрос,  415 моделей
   ├─ GATE:      415 → 388 → ~86            → 0 запросов, раздел 7.0
   ├─ fetch:     /api/v1/models/{id}/endpoints → ~86 запросов, конкурентность 8
   ├─ normalize: единая плоская схема, парсинг pricing.overrides
   ├─ snapshot:  data/snapshots/YYYY-MM-DD.json  (append-only)
   ├─ diff:      сравнение с data/latest.json    → changes.json   [MVP-1]
   ├─ compute:   фильтры → пороги → зоны → статусы → shortlist.json
   ├─ render:    report.md + index.html (шаблон, без билд-системы)
   ├─ commit:    в main
   └─ notify:    Telegram sendMessage                              [MVP-1, опц.]
              │
   GitHub Pages ← публикует из main
```

### Оценка выполнимости — по пунктам, честно

| Шаг | Выполнимо | Риски |
|---|---|---|
| fetch models | **да** | 1 запрос, без авторизации. **Только метаданные — не цена** (см. 5.1.4) |
| scope gate | **да** | 0 запросов, чистая функция от `/models`. Риск — невидимая ошибка отбора, см. процедуру в 7.0 |
| fetch endpoints | **да, обязательно** | **~86 запросов после гейта** (было ~403). Митигация: конкурентность 8, ретрай с backoff. **Не опционально:** без этого шага цены неверны |
| normalize | **да** | `pricing.overrides` требует явной обработки — 60 моделей |
| snapshot в git | **да** | после гейта ~86 моделей × ~1 КБ ≈ **13 КБ/день** → ~5 МБ/год. Хранить нормализованный срез, не сырой ответ. `gate_rejected.json` — только slug+причина |
| diff | **да** | требует стабильных ключей. `canonical_slug` подходит; `id` — нет (алиасы) |
| compute | **да** | чистая функция от снапшота |
| render | **да** | шаблонизация в один HTML-файл, без сборки, без npm |
| commit из Actions | **да** | стандартно; нужен `permissions: contents: write` |
| GitHub Pages | **да** | публикация из `main`, задержка обновления до ~1 минуты |
| Telegram из Actions | **да, lightweight** | bot token + chat id в secrets, один HTTP-запрос. **Хрупкость:** секреты недоступны в PR-форках; при ошибке отправки шаг падает — делать `continue-on-error`, чтобы не ронять весь пайплайн из-за уведомления |

### Явные ограничения схемы

1. **Cron в GitHub Actions неточен** — запуск может задержаться на 5–30 минут при нагрузке, а иногда пропускается. Для суточного дайджеста несущественно. Для алертов «скидка пропала» с требованием реакции за час — **недостаточно**, и это надо признать заранее: real-time алерты потребуют другой инфраструктуры, что и есть точка слома static-first.
2. **Actions отключаются на неактивных репозиториях** (~60 дней без коммитов). Здесь пайплайн сам коммитит ежедневно, поэтому не грозит.
3. **Нет состояния пользователя** — по построению. Любая персонализация требует пересмотра архитектуры.
4. **Публичный репозиторий** — снапшоты цен видны всем. Это нормально: данные публичные.

### Чего нет и не будет в ранних стадиях

Бэкенда, базы данных, авторизации, очередей, Docker, Kubernetes, фронтенд-фреймворка, системы сборки, CDN, аналитики.

## 12. Risks and disruptive feedback scenarios

### 12.1 Продуктовые риски

| Риск | Вероятность | Влияние | Реакция |
|---|---|---|---|
| **Автор не меняет конфиг ни разу** (H1 провалена) | средняя | критическое | Разобраться: рекомендации неверны или задача не болит? Если второе — направление закрыто, и это честный результат |
| **Изменений слишком мало, дайджест пуст** (H2) | средняя | высокое | Понизить порог значимости; перейти на недельную периодичность |
| **Рекомендации дрожат день ото дня** | **высокая** | высокое | Dominance with margins + гистерезис: смена дефолта только при подтверждении 2 дня подряд |
| **«Я и так это знал»** | средняя | высокое | Продукт не добавляет информации. Смещаться в change detection, где память человека объективно хуже |
| **Внешняя аудитория безразлична** (H6) | **высокая** | низкое | Ожидаемо. Фиксируем как результат, не как провал |
| **Скидки концентрируются у слабых моделей** | **высокая** (данные подтверждают) | среднее | Статус «Big discount, but not my safe default» существует именно для этого |

### 12.2 Технические риски

| Риск | Реакция |
|---|---|
| **`benchmarks.artificial_analysis` исчезнет** (недокументировано) | Деградация: ручной `data/overrides.json` с индексами для топ-40 моделей. Резервный путь — Data API `/api/v1/benchmarks` с ключом (5.1.8) |
| **Гейт отсекает нужную модель** | Невидимая ошибка — метрика не сработает. Митигация: ежедневный просмотр `gate_rejected` первую неделю + разовый полный прогон как приёмочный тест |
| **Гейт «дрожит»: набор меняется день ото дня** | Пороги топ-20 чувствительны к границе. Митигация: гистерезис — модель покидает набор только после 2 дней подряд вне порога |
| **Цены несопоставимы из-за разных reasoning-дефолтов** | Реальный дефект текущей логики: `glm-5.3` с default `max` сравнивается с `gemini-3.7-flash` с default `medium`. Митигация PoC — явная метка effort в карточке и дисклеймер; MVP-2 — замер |
| **G6 впускает устаревшие модели** | Накопленные битвы не исчезают, старые модели набирают категории со временем. Митигация — возрастной фильтр 180 дней (без него +65 моделей вместо +15) |
| **`pricing.discount` окажется уже применённым к прайсу** | Не показывать «было/стало», только факт скидки. Проверить эмпирически на первой неделе |
| **Rate limiting на 400+ запросов** | Конкурентность 8, backoff, суточный кеш эндпоинтов для моделей с неизменной ценой |
| **Рост репозитория** | Нормализованные снапшоты (~60 КБ/день), не сырые |
| **Cron пропускается** | Допустимо для суточного цикла; для алертов — признанное ограничение |
| **Формат API изменится** | Схема-валидация на входе; при несовпадении пайплайн падает громко, а не публикует мусор |

### 12.3 Disruptive feedback — заготовленные реакции

| Что могут сказать | Реакция |
|---|---|
| «Нам важнее alerts, чем ranking» | **Ожидаемо, согласны.** Ranking в PoC — способ накопить историю. Ускоряем MVP-1 |
| «Нам не нужен Hermes» | Hermes-интеграция изолирована в MVP-2 и не влияет на ядро. Для автора она — главная ценность; для внешних она опциональна |
| «Мы не используем OpenRouter» | Серьёзный удар: вся цена завязана на его прайс. Но модели-то те же. Смягчение: показывать вендорские цены отдельно. Полный пересмотр — только при массовом сигнале |
| «Не хотим сайт, шлите в Telegram» | Готовы: артефакт уже есть, канал добавляется одним шагом workflow |
| **«Полезнее, когда скидка пропала»** | **Уже заложено как приоритетный сигнал.** Лучший из возможных фидбеков |
| «Нужен safe default, а не Pareto» | **Уже так.** Pareto сознательно не в основе логики |
| «Хочу сравнить с моими реальными расходами» | Другой продукт (`bothub-llm-dashboard`, отдельная ветка). Не тащим |

### 12.4 Что может обесценить направление целиком

1. **OpenRouter выпускает свой advisor.** Вероятность средняя, влияние — полное. Смягчение отсутствует; проект к этому моменту уже отработает карьерную задачу.
2. **Цены стабилизируются.** Если за месяц значимых изменений почти нет — продукт не нужен. Проверяется дёшево: H2 даёт ответ за 2 недели.
3. **Задача решается одним промптом.** «Какая модель дешевле для кода» — вопрос, на который LLM с веб-доступом отвечает неплохо. Защита продукта — не в ответе, а в **непрерывном наблюдении**: LLM не заметит, что скидка пропала вчера ночью.
4. **Автор перестаёт быть пользователем.** Если конфиг стабилизировался и его не хочется трогать — нулевой пользователь исчез, и продукт держать не на чем.

Пункт 3 — самый серьёзный интеллектуально, и его стоит явно разобрать в README и в статье. Он же формулирует настоящую ценностную границу продукта: **не «ответить на вопрос», а «заметить изменение, о котором ты не спрашивал»**.

## 14. Final recommendation

### 14.1 Что строить первым (PoC)

**Собрать за ~5 дней:**

1. GitHub Actions, суточный cron: `/models` → **scope gate** → `/endpoints` (~86 запросов) → нормализация → снапшот в git.
2. Логика: фильтры → `Q_min` → ценовые зоны → `value_ratio` → пять статусов (включая 🟠 cheaper provider).
3. Четыре task-профиля: `chat`, `code`, `longdoc`, `bulk`.
4. Артефакты: `shortlist.json`, `report.md`, `index.html`, `gate_rejected.json`.
3a. Метки reasoning в карточке (`default_effort`, `mandatory`) + дисклеймер о цене при дефолтном effort.
4a. Приёмочный тест: разовый полный прогон (388 моделей) против урезанного — подтвердить сохранение топа.
5. GitHub Pages из `main`.
6. `NOTES.md` — вести с первого дня.
7. README с честным аудитом данных, включая то, чего нет.

**Не строить:** графики, Telegram, дельты, алерты, поиск, фильтры, персонализацию, второй источник.

**Мерить:** число изменений конфига за 14 дней. Ноль — сигнал остановиться и разобраться.

### 14.2 Что строить вторым (MVP-1)

Change detection, секция «что изменилось» **выше** shortlist, `changes.json`, dominance with margins против дрожания, `pareto_rank` как бейдж. Telegram — только по подтверждённой потребности. Первый показ внешней аудитории с одним вопросом.

### 14.3 Что отложить

Hermes config advisor (главный кандидат MVP-2, но только после ≥3 ручных применений), персональные алерты, watchlists, Artificial Analysis как источник, настраиваемое соотношение in:out, scatter-график, любые аккаунты и БД.

### 14.4 Что валидировать на реальных людях в первую очередь

На **себе** — в таком порядке:

1. Меняю ли я вообще конфиг? *(без этого остальное неважно)*
2. Захожу ли я на сайт по своей воле через неделю?
3. Что вызывает более сильную реакцию — «подешевело» или «скидка кончилась»?
4. Хочется ли посмотреть на график?

На **внешних** — только после того, как на себе получены ответы:

5. Есть ли среди них люди с API-ручкой?
6. Что для них было бы полезнее ranking'а?

### 14.5 Что может обесценить всё направление

Кратко: OpenRouter делает это сам · цены оказываются стабильными · вопрос решается одним промптом к LLM · автор перестаёт трогать конфиг. Развёрнуто — 12.4.

### 14.6 Лучший формат доставки по умолчанию

**Для продукта:** `report.md` в репозитории. Диффы в git бесплатно дают историю продукта, читается без интерфейса, версионируется.

**Для карьерной цели:** статический сайт на GitHub Pages. Живая ссылка обязательна — работодатель не будет читать JSON.

**Telegram:** лучший канал для *одного* типа сообщения — «скидка пропала, ты платишь больше». Для всего остального — избыточен и быстро становится шумом.

Итог: **сайт + markdown с первого дня, Telegram — только под подтверждённый алертный сценарий.**

### 14.7 Fallback при слабом качестве данных

По степени ухудшения:

| Сценарий | Fallback |
|---|---|
| Индексы качества исчезли | Ручной `overrides.json` на топ-40 моделей, обновление раз в месяц. Продукт живёт |
| Discount оказался бесполезным | Переключиться на собственные ценовые дельты. Название «Discount» становится неточным — переименовать в **Model Choice Advisor** |
| Цены почти не меняются | Продукт превращается в «периодическую ревизию конфига» раз в месяц. Меньше ценности, но не ноль |
| Данные шумные и противоречивые | Сузиться до одного профиля (`code`, самый релевантный автору) и трёх моделей. Один точный ответ лучше четырёх сомнительных |
| API закрылся или сломался | Направление закрыто. Артефакт остаётся как задокументированный кейс с честным разбором — карьерная цель достигнута независимо |

Последняя строка — не пораженчество, а осознанный дизайн: проект устроен так, что **не может провалиться полностью**, потому что процесс задокументирован не хуже результата.

## Приложение A. Явные non-goals

Не входит ни в одну из трёх стадий:

- enterprise / multi-tenant платформа
- real-time streaming backend
- авторизация и аккаунты
- персонализированные профили пользователей
- тяжёлая аналитика и BI-дашборд
- предположение, что Hermes — основной целевой workflow
- предположение, что всем нужен сайт
- предположение, что всех интересуют Pareto-графики
- вычисление cost per task как точной величины
- перепубликация чужих бенчмарков как собственных данных
- поддержка всех 415 моделей в интерфейсе

**Отдельная рекомендация по агентным задачам.** У Gemini 3.7 Flash разрыв между `coding` (76.1) и `agentic` (45.1) составляет **31 пункт — самый большой в выборке**. Это наблюдение — аргумент в пользу того, чтобы **разделить профили `code` и `agentic`** уже в PoC, а не откладывать на MVP-2. Пять профилей вместо четырёх, данные для пятого уже есть (`agentic_index`, 168 моделей).
